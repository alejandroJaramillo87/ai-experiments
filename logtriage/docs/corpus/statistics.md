# Corpus statistics

Measured over the MongoDB Database Manual at corpus commit `88ec8192b924b31fb986cb03349c37b4fb8cf41e`,
manual version 8.3, with the hashing embedder.

These are not decoration. A chunker is a component whose output nobody reads — 15,000 passages
go by and the only visible signal is that retrieval feels about right — so the way a chunking bug
survives is by being invisible. Counting the things that can go wrong, and recording those
counts, is what turns "the corpus looks fine" into a number that can move.

Regenerate with `python -m logtriage index-kb --json`.
`scripts/docs/check_corpus_stats.py` fails the gate when this document and the index disagree.

## Chunking

| | |
|---|---|
| Chunks | 15,025 |
| Tokens per chunk | min 2, p50 123, p95 450, max 5,789 |
| Over `MAX_TOKENS` | 105 |
| Under `MIN_TOKENS` | 782 |
| Chunks carrying code | 4,918 |
| Code blocks intact | 8,394 of 8,394 |
| Heading depth | 1: 948, 2: 6,900, 3: 6,305, 4: 856, 5: 16 |

**Code-block integrity is measured, not assumed.** The chunker is built never to split a code
block, and this checks the property rather than trusting it: a block is intact if its text
appears verbatim inside a single chunk. The failure has no other symptom — a chunk holding half
a `createIndex` command reads exactly like a chunk holding a short one, and it is the actionable
half of a diagnostic page.

A statistic that reads 100% is worth nothing unless it can read less, so
`tests/test_kb_real_constructs.py` drives the metric both ways: a deliberately truncated chunk is
counted as broken.

**Heading depth has no zero row**, and that is the number to notice. Every chunk carries a
heading path, so every retrieved passage arrives with the breadcrumb that makes it interpretable
alone.

The 105 chunks over `MAX_TOKENS` are by design: a code block longer than the budget is kept whole
rather than split. The 782 under `MIN_TOKENS` are short sections and stubs, retrievable but
rarely useful.

## Content that could have been lost

| | |
|---|---|
| Include directives resolved | 7,862 of 10,292 |
| Unknown constants | 0 |
| Unexpanded `{+x+}` substitutions | 0 |
| Residual role syntax | 150 |

**Include resolution is most of the corpus.** Four pages in five pull content in with
`.. include::` — 7,350 directives across 1,281 of 1,611 pages — against a tree of fragments that
are never pages themselves. A reader that treats a page file as the page sees a fraction of the
manual and a great many dangling references.

The 2,430 that do not resolve are accounted for by category, and every category is a file the
documentation toolchain generates during a build or one that lives in another repository:

| Count | Category |
|-------|----------|
| 648 | Code examples, generated by the docs build |
| 441 | Extracts, generated from `includes/extracts-*.yaml` |
| 140 | Other |
| 31 | Driver examples, sourced from the driver repositories |
| 11 | Release fragments, generated per release |

A corpus test fails if the unclassified count rises above a floor, because that would mean a
resolver bug rather than an absent file.

**The extracts are the one recoverable category left on the table.** They are a build system —
697 refs across 320 YAML files, 117 of them inheriting from another ref with template
replacement — and a partial reimplementation would silently produce text MongoDB does not
publish. Left unresolved and counted, deliberately.

## How to read these

Every number here was produced with `HashingEmbedder`, which has no semantics. The chunking
figures are about the corpus and hold regardless of embedder; the embed time does not, and no
retrieval-quality number appears in this document because none has been measured. See
[../verification/README.md](../verification/README.md).
