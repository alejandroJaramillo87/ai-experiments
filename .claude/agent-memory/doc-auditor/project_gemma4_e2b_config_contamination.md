Observed 2026-08-05 while auditing `docs/models/gemma-4.md` against
`gemma4-safetensors.txt` (transcript generated by
`scripts/models/gemma4_header_transcript.sh` on host Rico).

`/mnt/ai-data/models/hf/gemma-4-E2B/config.json` is **E4B's config file**, not E2B's:

- `git hash-object` on it returns `080fd8d51bb6e846df168157c9d57b928a2a2687`, which is
  byte-for-byte E4B's blob (both directories report the same hash and the same 5105-byte
  size).
- Its contents claim 42 layers / `hidden_size` 2560 / `intermediate_size` 10240 /
  `num_key_value_heads` 2 / `num_kv_shared_layers` 18 / `use_double_wide_mlp` false, while
  the E2B `model.safetensors` in the same directory holds 35 layers at `hidden_size` 1536
  with 15 MLPs at 6144 and 20 at 12288.
- The transcript script reads `"$dir/config.json"` for both the hash and the dump, so this
  is not a script bug — the file on disk is wrong.

**Why:** The E2B weights are genuinely a smaller model (10.2 GB vs 16.0 GB), so the weights
are authoritative and the config is the contaminated artifact. A reviewer who treats the
transcript's `gemma-4-E2B — config.json` section as ground truth will "correct" the
document's entire E2B column into E4B's numbers and destroy it.

**How to apply:** Until the host confirms a re-download, treat every E2B scalar that only
`config.json` can supply (`num_kv_shared_layers`, `sliding_window`,
`max_position_embeddings`, `layer_types` indices, `use_double_wide_mlp`, rope thetas) as
**unverified**, and verify the rest from safetensors shapes. `docs/models/gemma-4.md` is a
verification-claiming spec document, not an aspirational roadmap — its forward-looking
hedges are confined to its own "Open questions" section, and everything else in it is fair
game for drift reporting. Its E4B content checked out exactly. Related:
[[dual-ssd-identity-conflict]] — same failure shape: a file-level claim that only host
evidence can adjudicate.
