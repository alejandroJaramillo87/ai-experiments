# Benchmark results

The repository's recorded inference measurements, and what each one is still worth.

There is one entry. Everything else the repository has claimed about its own performance
traces back to it, which is why it has a document to itself rather than a section inside the
settings guide it was originally filed under.

## The 26.2 percent CPU figure

**Superseded — awaiting re-measurement with `python -m bench`.** The figures below are
retained because they are the only before-and-after pair the repository has, and because a
new measurement has to be reconciled against them. Four things disqualify them from being
quoted as current:

- **Measured at 12 cores.** The run used `cpuset 0-11` and `THREADS=12`; the llama-cpu
  service in `docker-compose.inference.yaml` now runs `cpuset 0-15` and `THREADS=16`.
- **The model is a mixture of experts.** Both arms served
  `Qwen3-Coder-30B-A3B-Instruct-IQ4_XS` — roughly 3B active parameters of 30B total. An
  MoE's decode rate moves with which experts a prompt routes to, and the figure was
  presented as the CPU track's headline without recording the architecture. It is now
  recorded in `MODELS` in `bench/registry.py`.
- **Prefill and decode are conflated.** `tokens_per_second` in the archived files is
  `completion_tokens / total_time`, so prefill is folded into a decode-shaped figure. A
  change to either phase moves it, and it identifies neither.
- **The generating script is not in the repository.** The two JSON files under
  [../optimizations/bios/](../optimizations/bios/) cannot be regenerated by anything in the
  tree.

Recorded figures, on those terms:

| Quantity | Value | Basis |
|----------|-------|-------|
| Before optimizations | 28.09 tokens/second | End-to-end average, prefill included |
| After optimizations | 35.44 tokens/second | Same basis |
| Performance gain | 26.2 percent | Ratio of the two above |
| Consistency improvement | 59 percent reduction in standard deviation | A derivation, not a stored field |

The consistency figure warrants the qualifier: the archived files hold per-prompt standard
deviations, and the quoted 59 percent is a derivation whose method is not recorded with it.

### Re-anchoring it

Run the arms the current configuration actually uses:

```bash
python3 -m bench noise --service llama-cpu --model qwen3-coder-30b-a3b-IQ4_XS
python3 -m bench run   --service llama-cpu --model qwen3-coder-30b-a3b-IQ4_XS \
    --profile publish --arm t16:THREADS=16 --arm t12:THREADS=12
```

Entry B7 of [../verification/bench/bench.md](../verification/bench/bench.md) is where that
happens, and it states what the re-measurement can and cannot settle: the thread count is one
of several changes the 26.2 percent bundled together, so the new number replaces the old one
rather than confirming or refuting it.

## Why this document exists

[method.md](method.md) states the rule the figure above breaks: a measurement is of a change,
with every other layer held at a named reference state, and the result is valid only at that
state. The 26.2 percent was measured against a configuration that no longer exists, by a
script that no longer exists, on an architecture nobody recorded.

Filing it beside the BIOS and OS settings it partly measured is what let it be restated
elsewhere as a validated property of those settings. A measurement outlives the
configuration it measured; the document that owns the configuration keeps changing under it.
